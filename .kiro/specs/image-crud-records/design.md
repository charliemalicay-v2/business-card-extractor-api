# Design: Image Storage & Full CRUD for Business Card Records

## Decisions (resolving requirements.md Open Questions)

1. **Delete-on-storage-failure ordering:** delete the DB row regardless of whether the storage
   delete succeeds. The storage delete is attempted first and its failure is logged (not raised)
   — an orphaned blob is preferable to a record the user can't get rid of. Rationale: this API has
   no background job/retry infrastructure, so "abort and let them retry" has no real retry path;
   simplicity wins.
2. **Update verb:** `PATCH /cards/{id}` (partial update), for consistency with the existing
   `PATCH /cards/{id}/review` endpoint and because all fields are optional in the update payload.
3. **Local backend URL exposure:** `GET /cards/{id}/image` is unauthenticated, matching every
   other endpoint in this API (there is currently no auth layer anywhere).
4. **Multi-backend migration/backfill:** out of scope. Switching `IMAGE_STORAGE_BACKEND` after
   go-live does not migrate previously-stored images; existing records keep referencing whatever
   backend they were written under. (Noted as a limitation, not silently handled.)

## Overview

Introduce an `ImageStorage` abstraction with three implementations (`local`, `s3`, `supabase`)
selected by config. Replace the record's `image_filename` string column with an
`image_storage_key` (the backend-agnostic reference) plus keep `image_filename` for display
purposes (original upload name). Add `PATCH /cards/{id}` and `DELETE /cards/{id}` routes. Add
`GET /cards/{id}/image` for the local backend. Response schemas gain an `image_url` field computed
at read time by asking the active `ImageStorage` for a URL given the stored key.

### Component: `ImageStorage` interface

```python
class ImageStorage(Protocol):
    def put(self, key: str, data: bytes, content_type: str) -> None: ...
    def delete(self, key: str) -> None: ...
    def url(self, key: str) -> str: ...
```

- `key` is generated by the caller (card_processing_service / update handler) as
  `f"{uuid4()}{ext}"` — backend implementations never invent their own naming scheme, so the same
  key is usable across backends and stored verbatim in `image_storage_key`.
- `delete()` must be idempotent (no error if the key doesn't exist) since it's also called for
  cleanup after a failed create (Requirement 1.6) and on record delete.
- `url()` for `local` returns the app's own `/cards/{id}/image` path (constructed by the caller,
  not by `LocalImageStorage` itself, since it doesn't know the record id — see below).

Because `local`'s URL is keyed by record id (not storage key) while `s3`/`supabase` URLs are keyed
by storage key, `url()` on the interface only covers `s3`/`supabase`. The response-building code
special-cases `local`:

```python
def build_image_url(record) -> str | None:
    if record.image_storage_key is None:
        return None
    if settings.image_storage_backend == "local":
        return f"/cards/{record.id}/image"
    return image_storage.url(record.image_storage_key)
```

This keeps `ImageStorage` simple (no record/id awareness) while still satisfying Requirement 2.3
(local URLs go through our own streaming endpoint).

### `LocalImageStorage`

- `put`: writes to `Path(settings.image_storage_local_dir) / key`, creating the dir if missing.
- `delete`: `Path(...).unlink(missing_ok=True)`.
- `url`: not used (see above); raises `NotImplementedError` to make the special-casing explicit
  rather than silently returning something wrong.
- New route `GET /cards/{id}/image`: looks up the record, 404s if missing or
  `image_storage_key is None`, else streams the file with `FileResponse` and a content-type
  guessed from the stored filename extension.

### `S3ImageStorage`

- Constructed with `boto3.client("s3", region_name=..., aws_access_key_id=..., aws_secret_access_key=...)`
  (falls back to default credential chain if not set, so IAM roles work in deployed envs).
- `put`: `put_object(Bucket=..., Key=key, Body=data, ContentType=content_type)`.
- `delete`: `delete_object(Bucket=..., Key=key)` (S3 delete is already idempotent).
- `url`: `generate_presigned_url("get_object", Params={Bucket, Key: key}, ExpiresIn=settings.image_storage_url_ttl_seconds)`.

### `SupabaseImageStorage`

- Uses `supabase-py`'s storage client against `settings.supabase_url` /
  `settings.supabase_service_key`, bucket `settings.supabase_storage_bucket`.
- `put`: `storage.from_(bucket).upload(key, data, {"content-type": content_type})`; on "already
  exists" conflict (shouldn't happen given uuid keys, but defensive), use `update` instead.
- `delete`: `storage.from_(bucket).remove([key])` — treat a "not found" response as success
  (idempotent per the interface contract).
- `url`: if bucket is public, `storage.from_(bucket).get_public_url(key)`; otherwise
  `create_signed_url(key, settings.image_storage_url_ttl_seconds)`. Which mode is used is
  controlled by `settings.supabase_storage_public: bool`.

### Factory

```python
def get_image_storage() -> ImageStorage:
    backend = settings.image_storage_backend
    if backend == "local": return LocalImageStorage(settings.image_storage_local_dir)
    if backend == "s3": return S3ImageStorage(...)
    if backend == "supabase": return SupabaseImageStorage(...)
    raise RuntimeError(f"Unknown IMAGE_STORAGE_BACKEND: {backend!r}")
```

Called once at startup (module-level singleton via `app/api/dependencies.py`, same pattern as
existing `get_card_repository`), so the invalid-backend case fails fast (Requirement 1.5).

## Data Models

`business_cards` table changes (new Alembic migration):

```python
image_storage_key: Mapped[str | None] = mapped_column(String, nullable=True)
```

- `image_filename` (existing column) is kept as-is — it's the human-readable original filename
  for display, distinct from `image_storage_key` (the opaque backend key). Existing rows keep
  `image_filename` populated and get `image_storage_key = NULL`, satisfying Requirement 6 (their
  `image_url` computes to `null` via the `image_storage_key is None` check).
- No other schema changes needed; `updated_at` already has `onupdate=func.now()` so Requirement
  4.6 is free.

### Schema (`app/schemas/response.py`) changes

```python
class CardResponse(BaseModel):

        image_url=build_image_url(record),

```

```python
class CardUpdateRequest(BaseModel):
```

All fields optional (`exclude_unset=True` semantics, same pattern already used by
`ReviewResolutionRequest`/`resolve_review`).

## API Changes (`app/api/cards.py`)

### `PATCH /cards/{id}`
- Multipart form: optional `file: UploadFile | None`, plus the `CardUpdateRequest` fields as form
  fields (since it must accept both JSON-like fields and an optional file, this becomes a
  multipart endpoint like `POST /cards`, not a pure JSON body).
- 404 if record missing.
- 400 `invalid_update_payload` if neither fields nor file provided.
- If `file` provided: validate content-type/size same as create, `image_storage.put(new_key, ...)`,
  then after DB commit succeeds, `image_storage.delete(old_key)` if there was one (delete-after-
  commit ordering avoids leaving a record pointing at a deleted image if the DB write fails).
- Field updates applied via `repository.update(card_id, fields)`.
- Returns updated `CardResponse`.

### `DELETE /cards/{id}`
- 404 if missing.
- `image_storage.delete(record.image_storage_key)` (best-effort per Decision 1), then
  `repository.delete(card_id)`.
- 204 No Content.

### `GET /cards/{id}/image` (local backend only, always registered)
- If active backend isn't `local`, or record/key missing, 404.
- `FileResponse(path, media_type=guessed_type)`.

## Repository Changes (`app/db/card_repository.py`)

- `update(card_id, fields: dict) -> BusinessCardRecord`: applies `setattr` for each key, commits,
  refreshes, returns record; raises if not found (route layer does the existence check first via
  `get_by_id`, consistent with the existing `resolve_review` pattern).
- `delete(card_id) -> None`: `session.delete(record); session.commit()`.

## Error Handling

| Scenario | Response |
|---|---|
| Unknown `IMAGE_STORAGE_BACKEND` | Startup failure (process exits), not an HTTP error |
| Storage `put` fails during create | `502 image_storage_unavailable`, no DB row created (process() raises before `card_repository.create`) |
| Storage `put` fails during update | `502 image_storage_unavailable`, no field changes applied (validate/upload before any DB write) |
| Update: record not found | `404 record_not_found` |
| Update: empty payload | `400 invalid_update_payload` |
| Delete: record not found | `404 record_not_found` |
| Delete: storage delete fails | Logged, DB delete proceeds, `204` still returned (Decision 1) |
| `GET /cards/{id}/image` on non-local backend or missing image | `404 record_not_found` / `404 image_not_found` |

New exception classes in `app/services/exceptions.py`: `ImageStorageError` (maps to 502 in
`app/api/exception_handlers.py`, following the existing pattern for `NotABusinessCardError` /
`OcrNoTextError`).

## Testing Strategy

- **Unit**: `LocalImageStorage` against a tmp dir (put/delete/idempotent-delete). `S3ImageStorage`
  and `SupabaseImageStorage` with mocked clients (boto3 `Stubber`, mocked supabase client) —
  verify correct calls, no real network access in unit tests.
- **Integration**: `card_processing_service.process()` with `LocalImageStorage` against a tmp dir,
  asserting the file exists after create and `image_storage_key` is set.
- **API tests**: extend existing `tests/` for `PATCH /cards/{id}` (field update, image replace,
  404, empty-payload 400), `DELETE /cards/{id}` (204, subsequent 404, 404 for missing id),
  `GET /cards/{id}/image` (200 with correct bytes/content-type, 404 for no image).
- **Regression**: existing create/list/get/review tests updated only where `image_url`/
  `image_filename` response shape changed; all must keep passing per Non-Functional Notes.
- Config-driven backend selection tested via `monkeypatch`-ing `settings.image_storage_backend`
  and asserting `get_image_storage()` returns the right type / raises on invalid value.
